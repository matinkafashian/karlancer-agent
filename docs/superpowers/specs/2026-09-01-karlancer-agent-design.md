# طراحی ایجنت خودکار کارلنسر

**تاریخ:** ۱۴۰۵/۰۶/۱۰ — 2026-09-01  
**وضعیت:** تأییدشده توسط کاربر در 2026-09-01  
**هدف:** ساخت ایجنت ۲۴ساعته روی VPS برای کشف پروژه، ارزیابی، تولید و ارسال پیشنهاد، و اعلام اولین پاسخ کارفرما.

## 1. دامنه و معیار پایان

سامانه باید:

1. همه پیام‌های جدید کانال عمومی `@karlancer_projects` را دریافت و هر پروژه را فقط یک‌بار ثبت کند.
2. لینک پروژه را با مرورگر لاگین‌شده باز و عنوان، توضیحات، مهارت‌ها، بازه بودجه و زمان را استخراج کند.
3. پروژه‌های برنامه‌نویسی و آموزشی مرتبط را قبول و کارهای صرفاً اپراتوری ابزارهای AI را رد کند.
4. پیشنهاد را با متن ثابت و لحن تأییدشده تولید کند.
5. مبلغ فرم را برابر بیشترین مبلغ بازه کارفرما و زمان را برابر زمان آگهی قرار دهد.
6. از حالت بدون ارسال به نیمه‌اتوماتیک و سپس تمام‌اتوماتیک ارتقا پیدا کند.
7. اولین پاسخ کارفرما را فقط یک‌بار به تلگرام کاربر گزارش دهد و پس از آن هیچ پاسخی برای کارفرما نفرستد.
8. با Docker Compose روی VPS اجرا، بازیابی و پایش شود.

پروژه زمانی کامل است که معیارهای پذیرش بخش 15 با شواهد اجرایی پاس شده باشند.

## 2. تصمیم‌های قطعی محصول

- منبع کشف پروژه: کانال عمومی پروژه‌های کارلنسر.
- تصمیم‌گیری فقط از روی هشتگ نیست؛ عنوان، متن کامل صفحه، مهارت‌ها و نوع خروجی بررسی می‌شوند.
- عبارت عمومی `AI` یا «هوش مصنوعی» به‌تنهایی هیچ امتیازی ندارد.
- یک نشانه فنی قوی مانند `RAG`، `YOLO`، `Telethon` یا شرح روشن برنامه‌نویسی برای بررسی کافی است؛ شرط سه یا چهار مهارت وجود ندارد.
- پروژه‌های آموزشی مرتبط پذیرفته می‌شوند.
- پروژه برنامه‌نویسی تولید یا پردازش تصویر/ویدئو با مدل یا API پذیرفته می‌شود.
- تدوین، تولید محتوا، ساخت کاراکتر، طراحی تصویر و کار صرف با ابزارهای آماده رد می‌شود.
- مبلغ پیشنهاد برابر سقف بودجه آگهی است.
- زمان پیشنهاد دقیقاً از آگهی کپی می‌شود.
- در متن گفته می‌شود مبلغ دقیق پس از بررسی جزئیات اعلام خواهد شد.
- در اولین پیشنهاد هیچ شماره، آیدی تلگرام یا دعوت به ارتباط خارج از کارلنسر قرار نمی‌گیرد.
- لینک‌های نمونه‌کار YouTube، GitHub و LinkedIn در متن ثابت باقی می‌مانند.
- ایجنت بعد از اولین پاسخ کارفرما وارد گفتگو نمی‌شود.

### 2.1 ناوردای ایمنی

این قواعد در همه modeها برقرارند و با prompt یا خروجی مدل قابل تغییر نیستند:

- mode پیش‌فرض همیشه `shadow` است.
- ارسال واقعی علاوه بر mode مناسب به kill switch مستقل `SUBMISSION_ENABLED=true` نیاز دارد؛ مقدار پیش‌فرض آن `false` است.
- تغییر از `shadow` به `assisted` و از `assisted` به `auto` فقط با اقدام صریح کاربر و ثبت audit event انجام می‌شود.
- submitter تنها مصرف‌کننده مجاز عملیات کلیک نهایی است؛ analyzer و generator به مرورگر دسترسی نوشتن ندارند.
- هر نتیجه مبهم پس از کلیک نهایی، خطای متوقف‌شونده است و retry خودکار submit ندارد.
- `human_handoff` حالت نهایی است و هیچ گذار خروجی به workflow ارسال پیام ندارد.
- از دست‌رفتن login، مشاهده CAPTCHA، شکست parse مبلغ/زمان یا تغییر selector فوراً مسیر ارسال را متوقف می‌کند.

## 3. معماری

سامانه از پنج جزء مستقل تشکیل می‌شود:

### 3.1 n8n Orchestrator

- اجرای زمان‌بندی‌ها و workflowها
- صف‌کردن پروژه‌های جدید
- فراخوانی worker از طریق HTTP داخلی
- ارسال اعلان و درخواست تأیید در تلگرام
- اجرای retryهای سطح workflow

n8n منبع حقیقت نیست؛ تمام وضعیت پایدار در PostgreSQL نگه‌داری می‌شود.

### 3.2 Python Worker

یک سرویس داخلی FastAPI با مسئولیت‌های زیر:

- خواندن و پارس کانال
- کنترل Playwright
- استخراج و اعتبارسنجی صفحه پروژه
- اعمال قواعد قطعی و تحلیل AI
- ساخت پیشنهاد
- ثبت پیشنهاد در سایت
- پایش اولین پاسخ

هر ماژول رابط مشخص دارد و می‌تواند مستقل تست شود.

### 3.3 Playwright Browser

- Chromium با `user-data-dir` پایدار
- ورود اولیه دستی از مسیر noVNC موقت
- ذخیره نشست در volume اختصاصی؛ رمز عبور در کد یا دیتابیس ذخیره نمی‌شود
- کلیک، خواندن و ارسال فقط با selectorهای قطعی
- AI اجازه انتخاب مختصات، کلیک یا ارسال فرم ندارد
- در صورت تغییر DOM، ارسال متوقف و snapshot و screenshot خطا ذخیره می‌شود

Stagehand و Skyvern در MVP استفاده نمی‌شوند. اگر selectorها مکرراً بشکنند، بعداً فقط به‌عنوان ابزار بازیابی بررسی می‌شوند.

### 3.4 PostgreSQL

منبع حقیقت برای پروژه‌ها، تصمیم‌ها، پیش‌نویس‌ها، ارسال‌ها، پاسخ‌ها و رخدادها است.

قیود ضروری:

- `canonical_project_url` یکتا
- `channel_message_id` یکتا
- برای هر پروژه حداکثر یک رکورد ارسال موفق
- برای هر ارسال حداکثر یک اعلان اولین پاسخ

### 3.5 Telegram Bot

فقط برای ارتباط با مالک سامانه استفاده می‌شود:

- گزارش خطا و انقضای نشست
- نمایش پیش‌نویس در حالت نیمه‌اتوماتیک
- فرمان‌های تأیید، رد و ویرایش در مرحله تست
- اعلان اولین پاسخ کارفرما همراه خلاصه و لینک گفتگو

این بات هیچ ارتباطی با کارفرمای کارلنسر ندارد.

## 4. جریان داده

1. n8n هر ۶۰ ثانیه کانال را بررسی می‌کند.
2. worker پیام‌های جدید را parse و URL را canonical می‌کند.
3. PostgreSQL پیام یا URL تکراری را رد می‌کند.
4. پروژه جدید وارد صف استخراج می‌شود.
5. Playwright صفحه پروژه را باز و داده‌ها را استخراج می‌کند.
6. validator وجود توضیحات، بودجه، زمان و دکمه پیشنهاد را بررسی می‌کند.
7. Rule Engine پروژه‌های قطعیِ نامرتبط را حذف می‌کند.
8. LLM Analyzer برای پروژه‌های باقی‌مانده خروجی JSON ساختاریافته تولید می‌کند.
9. Proposal Generator متن را می‌سازد و validator آن را کنترل می‌کند.
10. رفتار بعدی با mode جاری تعیین می‌شود: ذخیره، انتظار تأیید یا ارسال.
11. پس از ارسال موفق، پروژه وارد پایش پاسخ می‌شود.
12. اولین پیام کارفرما خلاصه و یک‌بار به تلگرام ارسال می‌شود.
13. وضعیت پروژه `human_handoff` می‌شود و هر نوع پاسخ خودکار ممنوع است.

## 5. ماشین حالت پروژه

- `discovered`: پیام کانال ثبت شده است.
- `extract_pending`: منتظر خواندن صفحه است.
- `extracted`: داده معتبر صفحه ذخیره شده است.
- `rejected`: نامرتبط است و ادامه نمی‌یابد.
- `needs_review`: تحلیل مطمئن نیست و به کاربر گزارش می‌شود.
- `eligible`: برای پیشنهاد مناسب است.
- `drafted`: متن معتبر تولید شده است.
- `awaiting_approval`: در حالت نیمه‌اتوماتیک منتظر تصمیم کاربر است.
- `submit_pending`: آماده ارسال است.
- `submitted`: موفقیت ارسال از صفحه سایت تأیید شده است.
- `reply_watch`: منتظر اولین پاسخ کارفرما است.
- `reply_notified`: اعلان تلگرام با موفقیت ارسال شده است.
- `human_handoff`: ادامه گفتگو فقط توسط کاربر انجام می‌شود.
- `retryable_error`: خطای موقت و قابل retry.
- `paused_error`: نیازمند ورود دستی، CAPTCHA، اصلاح selector یا تصمیم کاربر.

گذار به عقب مجاز نیست، مگر retry همان عملیات ناتمام. عملیات ارسال idempotent است.

## 6. دریافت پروژه از تلگرام

MVP از صفحه عمومی `https://t.me/s/karlancer_projects` استفاده می‌کند تا به حساب شخصی تلگرام وابسته نباشد.

- شناسه پیام، عنوان، بودجه نمایشی، زمان، هشتگ‌ها و لینک سایت ذخیره می‌شوند.
- cursor آخرین پیام موفق در دیتابیس ثبت می‌شود.
- در هر poll چند پیام آخر دوباره خوانده می‌شوند تا پیام مرزی از دست نرود؛ unique constraints تکرار را حذف می‌کنند.
- در خطای شبکه، backoff برابر ۱، ۵ و ۱۵ دقیقه اعمال می‌شود.
- اگر ساختار HTML قابل parse نباشد، ingestion متوقف و هشدار ارسال می‌شود؛ cursor جلو نمی‌رود.

اگر صفحه عمومی در عمل ناپایدار باشد، adapter دوم با Telethon و نشست جداگانه جایگزین می‌شود، بدون تغییر در بقیه سامانه.

## 7. استخراج صفحه کارلنسر

داده خروجی استخراج:

- شناسه و URL canonical پروژه
- عنوان
- توضیحات کامل
- مهارت‌ها
- حداقل و حداکثر بودجه
- زمان آگهی
- وضعیت باز یا بسته بودن
- نام یا شناسه نمایشی کارفرما در صورت وجود
- URL فرم پیشنهاد

اعتبارسنجی قبل از ادامه:

- پروژه هنوز باز باشد.
- قبلاً از حساب کاربر روی آن پیشنهاد ثبت نشده باشد.
- سقف بودجه و زمان با اطمینان parse شده باشند.
- نشست کارلنسر معتبر باشد.
- CAPTCHA یا مانع امنیتی فعال نباشد.

در صورت شکست هرکدام، فرم ارسال نمی‌شود.

## 8. موتور انتخاب پروژه

### 8.1 حوزه‌های مثبت

- Python و اتوماسیون، API، scraping و backend مرتبط
- Machine Learning و Data Science
- Deep Learning و شبکه‌های عصبی
- Computer Vision و Image/Video Processing برنامه‌نویسی‌شده
- NLP، Speech، LLM، RAG و Vector Database
- AI Engineering، AI Agents و MLOps
- ربات Telegram، WhatsApp، Bale، Rubika، Eitaa، Gap، Soroush، Discord و پیام‌رسان‌های مشابه
- آموزش عملی یا نظری حوزه‌های بالا

فهرست کامل مترادف‌های فارسی و انگلیسی به‌صورت فایل پیکربندی versioned نگه‌داری می‌شود.

### 8.2 رد قطعی

- تدوین ویدئو یا ساخت کلیپ با ابزار آماده
- تولید تصویر، کاراکتر، آواتار یا گرافیک بدون توسعه نرم‌افزار/API
- تولید محتوا یا اپراتوری ChatGPT و ابزارهای AI
- مقاله‌نویسی، ترجمه یا ویرایش صرف بدون کد، مدل یا نرم‌افزار
- ورود اطلاعات و annotation دستی صرف

### 8.3 تحلیل معنایی

LLM باید JSON زیر را برگرداند:

- `decision`: `eligible | rejected | needs_review`
- `confidence`: عدد صفر تا یک
- `programming_deliverable`: شرح یک‌خطی خروجی فنی
- `matched_domains`: حوزه‌های منطبق
- `hard_negative`: دلیل رد قطعی یا null
- `ambiguities`: ابهام‌های مؤثر
- `recommended_questions`: صفر تا دو سؤال ضروری
- `reason`: دلیل کوتاه تصمیم

ارسال خودکار فقط وقتی مجاز است که:

- `decision=eligible`
- `confidence >= 0.85`
- `hard_negative=null`
- extractor و proposal validator بدون خطا باشند

موارد دیگر به `needs_review` می‌روند و حذف نمی‌شوند.

## 10. ارائه‌دهنده مدل

worker یک رابط ثابت با دو عملیات دارد:

- `analyze_project(project) -> AnalysisResult`
- `generate_proposal(project, analysis, style) -> ProposalDraft`

adapterهای نخست:

- API سازگار با OpenAI برای اجرای پایدار VPS
- Ollama برای آزمون مدل محلی

Codex به‌عنوان وابستگی production فرض نمی‌شود. استفاده از آن فقط پس از اثبات رابط رسمی مناسب برای اجرای unattended، شرایط مصرف و هزینه وارد adapter جداگانه می‌شود. این تصمیم مانع استفاده از Codex برای توسعه خود پروژه نیست.

انتخاب مدل با یک مجموعه ثابت حداقل ۲۰ پروژه انجام می‌شود و بر اساس صحت تصمیم، پایبندی به لحن، نرخ خروجی نامعتبر، زمان پاسخ و هزینه ثبت می‌شود.

## 11. حالت‌های اجرا

### Shadow

- پروژه‌ها خوانده، تحلیل و draft می‌شوند.
- هیچ فیلدی در سایت پر یا ارسال نمی‌شود.
- کاربر تصمیم و متن را بازبینی می‌کند.

### Assisted

- draft، مبلغ، زمان و لینک در تلگرام مالک نمایش داده می‌شود.
- فرمان `approve` پروژه را وارد صف ارسال می‌کند.
- `reject` پروژه را رد می‌کند.
- `edit` متن اصلاح‌شده را ثبت می‌کند.
- ارسال نهایی فقط پس از approval همان پروژه انجام می‌شود.

### Auto

- فقط پروژه‌های واجد شروط بخش 8.3 خودکار ارسال می‌شوند.
- هر دو شرط `mode=auto` و `SUBMISSION_ENABLED=true` باید برقرار باشند.
- سقف ایمنی پیش‌فرض ۳۰ ارسال در ۲۴ ساعت است؛ رسیدن به سقف سامانه را pause و به کاربر هشدار می‌دهد.
- تغییر mode در دیتابیس audit می‌شود.

## 12. ارسال پیشنهاد

پیش از کلیک نهایی:

1. worker دوباره وضعیت بازبودن پروژه را بررسی می‌کند.
2. دیتابیس و صفحه پیشنهادهای حساب برای نبود ارسال قبلی بررسی می‌شوند.
3. متن، مبلغ و زمان با validator کنترل می‌شوند.
4. مقادیر فرم پس از fill دوباره از DOM خوانده و مقایسه می‌شوند.
5. screenshot پیش از ارسال ذخیره می‌شود.
6. submit انجام و پیام موفقیت یا حضور پیشنهاد در حساب بررسی می‌شود.
7. screenshot و URL نتیجه ذخیره می‌شوند.

اگر نتیجه مبهم باشد، retry ارسال انجام نمی‌شود؛ پروژه `paused_error` می‌شود تا ارسال دوگانه رخ ندهد.

## 13. تشخیص اولین پاسخ

- n8n هر ۱۲۰ ثانیه پروژه‌های `submitted` و `reply_watch` را صف می‌کند.
- worker بخش پیام‌ها/پیشنهادها را با Playwright بررسی می‌کند.
- پیام‌های سیستمی یا پیام خود کاربر پاسخ کارفرما محسوب نمی‌شوند.
- اولین پیام جدید کارفرما با شناسه یا hash متن ثبت می‌شود.
- گزارش تلگرام شامل عنوان پروژه، خلاصه پیشنهاد ارسال‌شده، متن یا خلاصه پاسخ، زمان و لینک مستقیم گفتگو است.
- پس از موفقیت Telegram API، `reply_notified_at` ثبت و وضعیت `human_handoff` می‌شود.
- هیچ endpoint یا workflow برای پاسخ‌دادن به کارفرما ساخته نمی‌شود.

## 14. خطا، امنیت و عملیات VPS

- تمام secretها فقط در `.env` خارج از Git یا Docker secrets قرار می‌گیرند.
- logها شامل رمز، cookie، token، متن کامل session storage یا اطلاعات ورود نیستند.
- volume نشست کارلنسر جدا و فقط در اختیار worker است.
- خطاهای شبکه سه retry با backoff دارند.
- خطای login، CAPTCHA، selector یا نتیجه مبهم ارسال retry خودکار ندارد و هشدار می‌دهد.
- containerها healthcheck و restart policy دارند.
- PostgreSQL روزانه backup می‌شود و حداقل هفت نسخه نگه‌داری می‌شود.
- n8n و noVNC عمومی نیستند؛ دسترسی از firewall و SSH tunnel انجام می‌شود.
- حداقل VPS برای یک stack: دو vCPU، چهار GB RAM و ۳۰ GB SSD.
- برای سه یا چهار ایجنت مستقل: چهار vCPU و هشت GB RAM، Compose project و volume و secret جدا برای هر ایجنت، و resource limit الزامی است.

## 15. آزمون و معیارهای پذیرش

### واحد و fixture

- نرمال‌سازی فارسی و انگلیسی، URL و مبلغ/زمان
- dedup پیام و پروژه
- قواعد مثبت و منفی
- اعتبارسنجی JSON مدل
- validator متن، مبلغ، زمان و اطلاعات تماس
- تمام گذارهای مجاز ماشین حالت
- idempotency ارسال و اعلان پاسخ

### Shadow واقعی

- حداقل ۲۰ پروژه اخیر شامل نمونه‌های مناسب و نامناسب پردازش شوند.
- هیچ درخواست submit به سایت انجام نشود.
- حداقل ۹۰٪ تصمیم‌ها با نظر کاربر منطبق باشند.
- هیچ پروژه دارای hard negative به `eligible` نرود.
- حداقل شش draft از سه گروه ساده، مبهم و آموزشی تأیید شوند.

### Assisted واقعی

- حداقل سه پیشنهاد متوالی با تأیید کاربر ارسال شوند.
- مبلغ و زمان هر سه دقیق باشند.
- ارسال تکراری صفر باشد.
- متن نیازمند اصلاح اساسی نباشد.

### Auto واقعی

- mode فقط با اقدام صریح کاربر فعال شود.
- حداقل سه ارسال نخست audit شوند.
- اولین پاسخ آزمایشی/واقعی دقیقاً یک اعلان تولید کند.
- لینک گفتگو معتبر باشد و پس از اعلان هیچ پاسخ خودکاری ایجاد نشود.

### استقرار

- `docker compose up -d` تمام سرویس‌ها را سالم کند.
- reboot VPS سرویس‌ها را بدون دخالت دستی برگرداند.
- backup و restore دیتابیس یک‌بار آزمایش شود.
- انقضای نشست و شکست selector به‌صورت کنترل‌شده ارسال را متوقف و هشدار ایجاد کنند.
